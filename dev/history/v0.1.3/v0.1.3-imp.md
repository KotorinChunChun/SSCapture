## 2. 配布構成と識別の統一（R1・R2）

- 通常検証後、毎回新しい作業先へ自己完結型の本体と管理補助を発行する。利用中の`artifacts/app`、導入済みディレクトリ、`data`から配布物を集めない。
- ルートに`SSCapture.exe`一式、導入用`tool.json`、`README.md`、必要な説明書・ライセンスを配置する。補助は`maintenance/`配下へランタイム・依存物も含める。補助EXE一個だけのコピーは禁止。
- 元のtool.jsonの開発用`executable`は開発導線として維持し、導入用コピーでは`executable`と`installedExecutable`を`SSCapture.exe`へ揃える。ID・name・AppId・能力は変更しない。`repositoryUrl`は`https://github.com/KotorinChunChun/SSCapture`とする。
- 製品版、FileVersion、AssemblyVersion、manifest、JSON、setup登録版、公開台帳の対応を一つの版から検査する。EXEのProductNameも必須条件に加える。
- ルートREADMEは導入利用者向けに生成する案を採る。配布する`docs/usage.md`等への相対リンクを保ち、配布しない開発資料・ソース・版別記録へのリンクは、公開承認時に固定したタグのGitHub参照へ変換する。リンクを消して検査を通すだけにしない。
- `tool.json`のmanual/readme/iconと、配布ドキュメント内のローカルリンクを正規化して再帰検査する。絶対パス・パス越境・リンク経由の越境・存在しない参照を拒否する。任意のREADME参照を理由に`dev`全体や利用者ファイルをコピーしない。
- 追加ファイルは明示した配布目録で管理し、相対パス・サイズ・SHA-256を保持する。文書、maintenanceの依存物、言語リソースそれぞれに許可範囲を設ける。

## 3. 管理補助とsetupの連携（R3・R5）

### 補助の採用方針

- [標準管理製品契約](../../../../../docs/development/definition-managed-products.md)と[共通インストーラー](../../../../../installers/product.iss)の処理を基準に、SSCaptureの独立Git側で補助をビルド・検証する。
- 共通Maintenanceの依存ソースを採用コミット・ライセンス・ハッシュ付きで固定して再利用し、SSCapture固有の旧版検証を追加する案。新規プロジェクト名・配置は実装時に確定する。親の未コミット内容や隣接checkoutの最新状態へ暗黙に依存させない。
- 親の`InstallationDetector`、製品許可表、導入ボタンの判定は変更しない。共通処理の修正を親にも適用する必要が判明した場合は、別担当へ根拠を引き継ぎ、勝手に親へ書き込まない。
- 通常の更新・削除は厳格なtool.json、正式登録、実EXE、配置の照合を必須とする。例外経路は次節の「tool.jsonが欠落した既知0.1.2の更新」に限定し、削除や一般製品の検出へ広げない。

### 更新

1. 新規導入／通常更新／旧0.1.2の限定修復を、既存ファイルへ書き込む前に判定する。不明な既存ファイルがある場所をクリーン導入扱いにしない。
2. setupに同梱した新しい補助を一時領域へ展開し、その補助で対象を照合する。更新対象フォルダー内の旧補助や未確認EXEを代わりに起動しない。
3. 同一利用者・セッション・実行パス・PIDを照合した共通管理契約で正常停止を要求し、プロセス終了まで確認する。拒否、応答不明、PID変化、アクセス失敗は中止。強制終了しない。
4. 変更する配布所有ファイルと対象登録の更新前状態を退避してから置換する。退避・復旧の対象は所有が確認できたものだけとし、`data`や利用者の追加ファイルをフォルダー丸ごと巻き戻さない。
5. 更新後に新しい定義・EXE・登録先・対象版を照合する。失敗時はこの実行で変更した所有物だけの復旧を試み、復旧不能なら「要対応」として終了する。壊れた状態を成功・自動再起動で隠さない。

`AppMutex`はsetup/uninstallの起動時に確認されるため、現在の設定を残すと正常停止要求より先に利用者へ終了を求める。setup側の拒否を補助による検証付き正常停止へ置き換える案とし、アプリ自身の単一起動mutexは維持する。`CloseApplications=no`と`RestartApplications=no`も維持する。実装時は採用するInno版で順序を確認する。
根拠: [AppMutex](https://jrsoftware.org/ishelp/topic_setup_appmutex.htm)、[PrepareToInstall等のイベント](https://jrsoftware.org/ishelp/topic_scriptevents.htm)。

### 削除・取消・復旧

- 削除開始前に正常停止と対象照合を行い、所有記録・所有マーカー・現物の指紋が一致する管理予約だけを整理する。外部予約や他製品の予約には触れない。本体共通予約に関連する処理も共通の所有・依存条件から逸脱させない。
- 補助・依存物と復旧記録は、削除で失われる導入先の外にこの実行専用で保持する。利用者を限定し、改変・別製品・別実行の記録を拒否する。
- 現行共通補助の`recover`は実EXEや正式登録の照合を先に要求するため、部分削除後には動けない可能性がある。事前に検証した対象・所有予約の復旧記録を使う専用経路を設計し、削除途中でも復旧できるか故障注入する。任意の未導入パスに対する汎用の照合省略にはしない。
- 取消・失敗時は当該操作が変更した予約・管理設定を復旧する。操作後の外部変更は上書きせず、復旧できなければ記録を残して利用者へ案内する。部分削除された製品ファイルは修正版setupによる修復が必要な場合を区別する。
- 正常削除の完了後も利用者設定・保存画像・利用者配置の外部ツールを残す。`data/*`や導入先全体を消すワイルドカード削除を追加しない。

## 4. tool.jsonなしの旧0.1.2からの復旧（R4）

旧版限定の判定器をSSCapture側補助に新設する案。次の全条件を満たす場合だけ更新を許可する。

| 条件 | 必須の照合 |
| --- | --- |
| 対象識別 | 固定の`ss-capture` / `SSCapture` / `KotorinToys.SSCapture` |
| 正式登録 | 当該HKCU削除登録が存在し、DisplayName・DisplayVersionが既知0.1.2と一致 |
| 導入先 | 登録InstallLocationとsetup対象を正規化して一致確認。曖昧な相対パス・reparse point等は拒否 |
| 実EXE | 登録先のSSCapture.exeが存在し、ProductName・FileVersion・ProductVersionとアセンブリ版が0.1.2に一致 |
| 既知配布物 | 命令書のSHA-256を持つ旧setupを非実行展開して得た、旧EXE・アプリDLL等の識別用ハッシュと照合。照合前に起動しない |
| 欠落の範囲 | tool.jsonが存在しない場合だけ。存在するが壊れている／別ID／別AppIdの場合を欠落として扱わない |
| 削除登録の配置 | 削除プログラムの登録パスが同じ導入先に収まり、別の製品や場所を指していない |

- 判定成功は「このsetup実行で、この登録先の既知旧版を更新できる」という限定結果。通常の本体検出へ偽のtool.jsonを手置きしたり、本体を「導入済み」に見せかけたりしない。
- 停止要求と置換直前にも対象パス・PID・識別を再確認する。競合する更新や対象の差替えを検出したら中止する。
- `UsePreviousAppDir=yes`と同一AppIdを維持し、既存の日本語・空白を含むカスタム導入先へ上書き更新する。登録と違う場所を新しい既定先として採用しない。これは既定候補の継承だけでなく、補助で登録先との一致を必須にする。[Innoの既存導入先継承](https://jrsoftware.org/ishelp/topic_setup_usepreviousappdir.htm)
- 登録なし、実EXEなし、版違い、改変、登録先違いでは限定修復を拒否する。自動的なアンインストールやユーザーデータ削除で回避しない。

## 5. 利用者データと履歴（R4）

| 対象 | 方針・未確定事項 |
| --- | --- |
| `data`内の設定・前回範囲等 | 配布元に含めず、更新・削除の対象外。検証では処理前後のバイト列とハッシュを照合 |
| 保存画像・録画 | 導入先内外を問わず削除・移動・再命名しない。専用の架空データで保持を検証 |
| 利用者配置のFFmpeg/FFprobe/OneOCR等 | 新setupへ同梱せず、既存の配置と内容を保持する |
| ディスク上の履歴等の利用者ファイル | 存在するものは保持する。履歴名を推測して消さない |
| 現行のメモリー内撮影履歴 | 20件・256MiB上限で正常終了時に破棄される。旧0.1.2に永続化・退避経路がないため、更新で必須となる正常停止をまたぐ完全保持は現在の契約では保証できない |

2026年10月21日の回答で、メモリー履歴は設定に従い起動中のみ保持することで確定した。既存のKeepHistory、20件・256MiB上限、OFF時の消去、終了時の破棄を維持し、更新をまたぐ永続化は追加しない。

## 6. 配布拒否ゲートとランタイム（R6・R7）

- 新規候補`Test-ManagedPayload`へ管理適合検査を集約し、インストーラー生成前と生成後の非実行展開結果の両方へ適用する。テストや公開検査から同じ条件を呼ぶ。
- 必須物の個別欠落、空の定義、不正JSON、ID/AppId/name/EXE版/登録用定数の不一致、能力不足、repositoryUrl違い、説明書参照切れ、補助の依存物欠落を非0で拒否する。
- setupの非実行展開後、全同梱ファイルについて余分・欠落・相対パス・サイズ・SHA-256を発行元目録と比較する。setupの一時展開専用Maintenanceと通常導入用Maintenanceも別々に検査する。
- 目録自身に必須物がない場合も拒否する。旧版で行った「目録に書かれた全ファイルが一致」だけでは今回の欠落を検出できない。
- [本体の配布安全ゲート](../../../../../docs/security.md)と同じ禁止ファイル・リンク拒否・マスク済み秘密検査・失敗時中止を維持する。共通ゲートは[現在のスクリプト](../../../../../dev/scripts/test-public-payload-security.ps1)を採用コミット付きで参照する。
- 現行ゲートは親ワークスペースと親の版別ログ配下へパスを限定している。独立checkout向けに固定ソースを再利用する場合、SSCaptureの作業先・版別ログ先へ限定し直し、上限や拒否条件を緩めない。任意パス許可や親ソースの直接変更で解決しない。
- ランタイムの具体的な版は本案では固定しない。生成時に公式.NET 10リリースメタデータで最新修正版を確認し、採用値と取得日時を記録する。本体Desktop/Coreと補助Coreの全runtimeconfig・実体・ライセンスを検査する。親の現在の固定値もそのまま最新とみなさない。
- `.tools/dotnet`を優先する現行`common.ps1`と、SDK既定版を持つ`setup-sdk.ps1`も検証対象。PCに新しいSDKがあるだけで公開ランタイムが新しくなると仮定しない。
- 生成後から公開までに修正版が更新された場合は再検査し、古ければ再生成・再検証する。通信失敗、検査器の失敗、未知のランタイムは「検出なし」で通さない。
- 検査器・コンパイラー・非実行展開ツールは配布元とハッシュを固定する。FFmpeg等の別途配置方針は維持する。

## 7. 版確定・公開と利用者への案内（R8）

- 実装開始前にローカルとGitHubのタグ・Release、他担当の進行中資料を確認し、未使用のパッチ版を確定する。現時点のv0.1.3は候補であり、GitHub未使用を確認した結果ではない。
- 旧v0.1.2のタグ・assetは上書きしない。新しいEXEと同時に製品別JSON・SHA256SUMSを生成し、再生成したEXEへ古い台帳を組み合わせない。
- 公開承認前の成果物はローカル検証用として扱い、公開済みを示す記録やGitHubのタグ・Releaseを作らない。公開後の匿名再取得は別の承認工程に残す。
- 将来の復旧案内は「正規修正版setupを取得 → 既存の登録先へ手動更新 → 本体で再検出」の一度限りの手順とする。本体で無効になった更新ボタンを入口にせず、アンインストール、設定削除、tool.jsonの手置きは求めない。
- 終了拒否時は撮影・録画・出力等を完了して再試行する案内とする。検出理由の詳細表示は本体担当の別課題として引き継ぎ、本修正で安全確認を解除しない。
